# Разбор исходных скриптов из переписки с Kimi

Что было проверено: все файлы из четырёх «партий» кода в переписке — конфиги,
13 модулей main-процесса, preload, App.tsx и 7 компонентов, промпты агентов.

**Короткий вердикт.** Архитектура правильная и продуманная: разделение
main/preload/renderer, `contextIsolation: true`, типизированный мост через
`contextBridge`, разбиение по модулям, единый формат IPC-каналов, стриминг через
async-генераторы. Скелет менять не пришлось — проект здесь построен по той же
схеме, и большинство файлов узнаваемы.

Но **в исходном виде проект не собрался бы**, а если обойти ошибки компиляции —
не заработал бы: системные промпты агентов не загружались, стоимость запросов
считалась в 1000 раз выше реальной, выбранная в настройках модель Claude
уходила на эндпоинт Kimi, а Live Preview на современном Node.js падал при старте.

Ниже — что найдено и что сделано.

---

## A. Не компилировалось

**A1. `import * as archiver from 'archiver'`** (`export.ts`, `deploy.ts`)

При `esModuleInterop: true` namespace-импорт даёт необязательно вызываемый
объект — TypeScript отвечает `TS2349: This expression is not callable`.
→ Заменено на `import archiver from 'archiver'`.

**A2. `headers` внутри тела запроса Anthropic** (`api-client.ts`)

```ts
anthropic.messages.stream({ model, max_tokens, system, messages, headers: {...} })
```

`headers` — не поле тела запроса. Опции запроса передаются **вторым**
аргументом. → Исправлено; заодно beta-заголовок `prompt-caching-2024-10-01`
убран: кэширование промптов давно вышло из беты.

**A3. Нет `@types/node` в devDependencies**

`fs`, `path`, `process`, `__dirname`, `require` — всё это в main-процессе
требует типов Node. Работало бы только случайно, транзитивно через пакет
`electron`. → Добавлено явно.

**A4. Renderer никогда не проверялся типами**

`tsconfig.renderer.json` в проекте был, но ни один npm-скрипт его не вызывал:
`build` — это `tsc && vite build`, где `tsc` берёт корневой конфиг (только
main + preload), а Vite типы не проверяет вовсе. Поэтому баг с отсутствующим
`autoFixEnabled` (Kimi нашёл его сам в конце переписки) сборка не поймала бы —
и не поймала бы ни один следующий. → Добавлен скрипт `npm run typecheck`,
проверяющий оба конфига; renderer типизирован полностью.

---

## B. Падало в рантайме

**B1. Экспорт и деплой-экспорт не работали никогда** (`main.ts`)

```ts
registerExportIPC(mainWindow!)   // ← mainWindow здесь ещё null
registerDeployIPC(mainWindow!)
createWindow()                    // ← окно создаётся только тут
```

Восклицательный знак глушит предупреждение TypeScript, но не меняет значение:
в модули уходил `null`, и `dialog.showSaveDialog(null, …)` бросал TypeError при
первом же нажатии «Экспорт». → Модули получают геттер `() => mainWindow`, а не
значение.

**B2. `.github/workflows/deploy.yml` без создания папки** (`deploy.ts`)

`fs.writeFileSync` не создаёт промежуточные директории → `ENOENT` при выборе
Railway. → Все записи идут через хелпер с `mkdirSync({ recursive: true })`.

**B3. Live Preview не запустился бы на вашем Node** (`live-preview.ts`)

```ts
spawn('npm.cmd', ['run', 'dev'], { cwd, stdio: 'pipe' })
```

Начиная с Node 18.20 / 20.12 (исправление CVE-2024-27980) `spawn` отказывается
запускать `.cmd`-файлы без `shell: true` и бросает `EINVAL`. У вас Node 24 —
кнопка «Старт» не сработала бы ни разу. → Добавлен `shell: true`.

**B4. `createAutoFixTask` бросал исключение**

`throw new Error('Task not found')` внутри IPC-обработчика превращается в
отклонённый промис в renderer'е, где его никто не ловит. → Возвращает `null`.

## C. Логические ошибки

**C1. Стоимость завышалась в 1000 раз** (`api-client.ts`) — самая дорогая ошибка

```ts
return (inputTokens / 1000) * pricing.input + (outputTokens / 1000) * pricing.output
```

Цены в таблице заданы за **миллион** токенов (`{ input: 3.0, output: 15.0 }` —
это $3/$15 за 1M у Sonnet), а делитель — тысяча. Каждый запрос учитывался в
1000× дороже реального. Бюджет $10 «сгорал» бы примерно после 3000 токенов,
после чего приложение навсегда уходило в эконом-режим.

То же в UI: подписи `'$0.6/$0.6'` рядом с Kimi 8K подразумевали цену за 1K.

→ Деление на `1_000_000`, таблица цен приведена к «долларов за миллион»,
подписи в интерфейсе исправлены.

**C2. Выбранная модель уходила не тому провайдеру** (`api-client.ts`)

```ts
export function resolveProvider(agentId, forceHeavy = false) {
  if (agent.mode === 'claude') return { provider: 'claude', model: agent.heavyModel }
  if (agent.mode === 'kimi')   return { provider: 'kimi',   model: agent.model }
  return { provider: 'kimi', model: agent.model }   // ← mode === 'auto'
}
```

Режим по умолчанию — `auto`, и он **всегда** возвращает `provider: 'kimi'`.
При этом в Настройках можно выбрать агенту `claude-opus-4-…` — и эта строка
уходила бы в `POST api.moonshot.cn/v1/chat/completions`. Ответ — ошибка о
неизвестной модели.

→ Провайдер больше не хранится отдельно, а **выводится из имени модели**
(`claude-*` → Anthropic, иначе Moonshot) одной функцией, которая используется и
в main, и в renderer. Рассинхронизация стала невозможной по конструкции.

**C3. Системные промпты агентов не загружались вообще** (`file-manager.ts`,
`api-client.ts`, `mcp-server.ts`, `templates.ts`, `deploy.ts`, `export.ts`)

```ts
function getAppRoot(): string {
  if (process.env.NODE_ENV === 'development' || !process.resourcesPath) return process.cwd()
  return process.resourcesPath
}
```

Две проблемы сразу:

1. `NODE_ENV=development` в проекте нигде не выставлялся — ни в скриптах, ни в коде.
2. `process.resourcesPath` в Electron определён **всегда**, включая запуск из
   исходников.

Значит, в обычном `npm start` корнем становился
`node_modules\electron\dist\resources`. Там нет `.claude/agents/*.md`, поэтому
`loadSystemPrompt` каждый раз возвращал заглушку:

```
You are .claude/agents/admin-agent.md. Follow all instructions carefully.
```

То есть все четыре агента были одинаковыми и без ролей — центральная функция
приложения молча не работала. Туда же создавались шаблоны проектов и конфиги
деплоя. В собранном приложении это была бы попытка записи в Program Files.

→ Введён модуль `paths.ts` с явной рабочей папкой (по умолчанию
`Документы\AgentForge-Workspace`), сменяемой в Настройках. Промпты при первом
запуске записываются туда из встроенных значений по умолчанию.

**C4. История сессий копила дубли и теряла последний ответ** (`App.tsx`)

`saveCurrentSession()` вызывался внутри обработчика `done` и читал `messages`
**до** того, как в них попадал ответ агента, — в истории оставался диалог без
последней реплики. Плюс `id: ${activeAgentId}-${Date.now()}` генерировался
заново на каждое сохранение, поэтому один разговор превращался в десятки
записей.

→ Сохранение вынесено в эффект, срабатывающий после обновления сообщений;
id фиксируется один раз на агента (`sessionIdsRef`), в хранилище — upsert по id.

**C5. Сброс эконом-режима не работал**

```ts
export function resetEconomyMode(): void { economyMode = false }
```

Флаг снимался, но накопленный расход оставался выше лимита — `checkBudget()`
включал режим обратно на следующем же запросе. → Сброс обнуляет и счётчик,
о чём теперь прямо написано в модалке.

**C6. Бюджет захардкожен.** `checkBudget()` сравнивал с `10.0`, игнорируя
`getDailyBudget()`. → Лимит настраивается в UI и сохраняется.

**C7. Учёт токенов Kimi считал чанки** (`api-client.ts`)

```ts
if (delta) { outputTokens += 1; yield { type: 'chunk', text: delta } }
```

Это счётчик SSE-чанков, а не токенов. Реальный `usage` Moonshot в стриме не
присылает, если не попросить. → Добавлено `stream_options: { include_usage: true }`,
самодельный счётчик убран.

**C8. Ни один из трёх шаблонов проектов не запускался** (`templates.ts`)

Генерируемый `index.html` содержит `<script type="module" src="/src/main.tsx">`,
но `src/main.tsx` шаблон не создаёт — только `App.tsx`. `npm run dev` в такой
папке отдаёт 404 на входной модуль. Также не создавался `index.css`, который
импортируется. → Добавлен общий каркас фронтенда: `main.tsx`, `index.css`,
`tsconfig.json`, README; проверено, что все три шаблона создают полный комплект.

**C9. `docker build` фронтенда падал** (`deploy.ts`)

Dockerfile содержит `COPY nginx.conf /etc/nginx/conf.d/default.conf`, но
`nginx.conf` генератор не создавал. → Файл добавлен (с SPA-fallback и проксёй
на бэкенд).

**C10. Экспорт: отмена и «нечего экспортировать» неразличимы** (`export.ts`)

Обе ситуации возвращали `null`, и UI на отмену диалога показывал «Нечего
экспортировать». → Возвращается статус `ok | cancelled | empty | error`.

**C11. API-ключи не сохранялись.** Вводить заново при каждом запуске.
→ Шифруются через `safeStorage` (на Windows — DPAPI) и сохраняются. Если ОС
шифрование не даёт, ключи не пишутся на диск вовсе, и в UI об этом сказано —
класть их в открытый JSON хуже, чем спросить заново.

## D. Безопасность

**D1. `webSecurity: false`** (`main.ts`)

Отключает same-origin policy во всём renderer'е. Для встраивания dev-сервера в
`<iframe>` это не требуется: кросс-доменный iframe рендерится и при включённой
защите (блокируется только чтение его содержимого из JS, а это здесь не нужно).
→ Включено обратно; Live Preview проверен и работает.

**D2. MCP принимал абсолютные пути** (`mcp-server.ts`)

```ts
const fullPath = path.isAbsolute(filePath) ? filePath : path.join(getAppRoot(), filePath)
```

Пути приходят из renderer'а — то есть в перспективе из текста, сгенерированного
моделью. `mcpWriteFile` мог перезаписать любой файл, доступный пользователю.
→ Все пути разрешаются строго внутри рабочей папки (`resolveInWorkspace`);
выход за её пределы, включая `..` и абсолютные пути, отклоняется. Проверено
тестами.

**D3. Поиск по коду читал всё подряд** (`mcpSearchCode`)

Каждый файл читался как utf-8 без ограничения размера, без пропуска бинарников
и без лимита глубины — на реальном дереве с `node_modules` это зависание.
→ Лимит 512 КБ на файл, отсев бинарников по NUL-байту, пропуск
`node_modules/dist/.git/build/venv`, потолок в 100 совпадений.

**D4. Не было CSP.** Electron писал об этом предупреждение в консоль.
→ Добавлена политика в `index.html`: скрипты только свои, сеть из renderer'а
запрещена (всё идёт через IPC), iframe разрешён только для localhost.

**D5. Пароль БД в открытом виде.** `POSTGRES_PASSWORD: pass` прямо в
`docker-compose.yml`. → Вынесено в переменные окружения со значением по
умолчанию `change-me` и предупреждением в `DEPLOY.md`.

## Версия 1.1 — что изменилось после разбора

Разбор выше относится к исходным скриптам. Ниже — что добавлено уже поверх
собранного проекта.

### Список моделей вместо захардкоженного

В версии 1.0 список моделей был константой в коде — я специально не стал
угадывать актуальные имена моделей Moonshot и оставил только три
`moonshot-v1-*`. Теперь список **запрашивается у провайдеров**:
`client.models.list()` у Anthropic и `GET /v1/models` у Moonshot.

- Показывается ровно то, к чему есть доступ у конкретного ключа.
- Кэш на 10 минут; сбрасывается при смене ключа или эндпоинта Moonshot.
- Без ключа или при ошибке — встроенный список плюс текст причины,
  интерфейс остаётся рабочим.
- Кнопка **Проверить ключ** использует тот же запрос: это самый дешёвый
  способ проверки (не тратит токены).
- Для модели вне таблицы цен берётся средняя цена **её провайдера**, а не
  общая: иначе неизвестная модель Kimi считалась бы по тарифу Claude
  и завышала расход в несколько раз.

Попутно найден и исправлен баг: `fetchKimiModels` и `streamKimi` бросали
обычный `Error`, у которого нет поля `status`. Из-за этого понятные сообщения
(«Ключ отклонён», «Превышен лимит») работали только для SDK Anthropic, а для
Moonshot пользователь видел сырой JSON провайдера. Введён класс `HttpError`,
несущий код ответа.

### Интерфейс в стиле Photoshop

Полностью переписан слой представления; логика main-процесса не менялась.

- Палитра и метрики тёмной темы Photoshop вынесены в `renderer/theme.ts`.
- **Все эмодзи убраны** — из интерфейса, из промптов агентов
  (формат отчёта Tester'а стал `[CRITICAL] / [WARNING] / [OK]`) и из
  генерируемых шаблонов. Вместо них — набор штриховых SVG-иконок
  `renderer/icons.tsx`, нарисованных под панель инструментов Photoshop.
- Добавлена оболочка: строка меню с выпадающими списками (разделители,
  подменю, галочки, горячие клавиши), строка параметров, вертикальные рейки
  инструментов и панелей, строка состояния, рамки панелей с заголовками.
- Сообщения в чате перестали быть «пузырями»: теперь это строки журнала во всю
  ширину с шапкой (автор, время, модель) — так удобнее читать код, который
  агенты присылают чаще всего.
- Панели можно скрывать через меню **Вид**.

Мелкие исправления, найденные при визуальной проверке:

- Выпадающий список эндпоинта Moonshot молча показывал первый вариант, если в
  настройках лежал адрес не из списка. Теперь неизвестный адрес выводится
  отдельным пунктом.
- То же для модели агента: если модель пропала из списка провайдера, она
  показывается как «(нет в списке)», а не подменяется соседней.
- Путь к рабочей папке в строке состояния сокращался через `direction: rtl`,
  что переставляет куски пути местами. Заменено на явное сокращение середины.

### Проверка версии 1.1

- `npm run typecheck` — оба конфига, 0 ошибок; `npm run build` — успешно.

## Версия 1.2 — проекты, файлы, безрамочное окно, Markdown

### Проект как единица работы

Появилась сущность **Проект**: своя папка на диске, свои задачи, своя память
и **отдельный диалог с каждым агентом**. В main-процессе всегда есть один
активный проект — благодаря этому панелям (файлы, превью, деплой, экспорт,
шаблоны) не нужно передавать projectId, они спрашивают `getProjectDir()`.

- `projects.ts` — список проектов, активный проект, создание папок,
  `resolveInProject()` вместо `resolveInWorkspace()`.
- `chat-store.ts` — переписка по паре «проект + агент». Пришёл на смену
  журналу сессий: раньше одни и те же сообщения лежали и в состоянии
  renderer'а, и в `sessions.json`, и могли разойтись.
- `decomposition.ts` и `project-memory.ts` теперь хранят данные с ключом
  по проекту; старые плоские файлы автоматически переносятся в первый проект.
- Имя папки — транслитерация названия латиницей: папка становится рабочей
  директорией `npm` и контекстом сборки Docker, где кириллица регулярно
  ломает сторонние инструменты. Пустая папка переименовывается вместе
  с проектом, непустая — нет.
- Удаление проекта убирает его из списка, но **не трогает файлы на диске**.

### Обмен файлами

`file-ops.ts` — добавление файлов через системный диалог и перетаскиванием,
создание папок, переименование, удаление, открытие в проводнике. Всё строго
внутри папки проекта: путь из renderer'а проходит через `resolveInProject`,
попытка выйти через `..` отклоняется. Одноимённый файл не перезаписывается,
а добавляется как `file (2).txt`.

Перетаскивание использует `webUtils.getPathForFile`: в Electron 32+ свойство
`File.path` убрали, и наивный код получил бы пустой путь.

### Одна полоса сверху

Окно создаётся с `frame: false`, системного заголовка Windows больше нет.
Строка меню стала строкой заголовка: значок, меню, название проекта, кнопки
свернуть/развернуть/закрыть. Область перетаскивания задаётся через
`WebkitAppRegion`, кнопки и меню помечены `no-drag`.

### Markdown в чате

`markdown.tsx` — собственный разбор в React-узлы. Библиотеку не брал
намеренно: результат собирается из элементов, а не через
`dangerouslySetInnerHTML`, поэтому ответ модели не может протащить разметку
в DOM. Поддержаны заголовки, **жирный**, *курсив*, ~~зачёркнутый~~, `код`,
блоки кода с языком, списки, цитаты, таблицы, ссылки.

Копирование сделано через модуль `clipboard` Electron, а не
`navigator.clipboard`: страница грузится по `file://`, где Clipboard API
доступен не всегда.

### Найденные при проверке ошибки

**Зависание всего интерфейса на вложенной разметке.** `INLINE_RE` был
объявлен на уровне модуля с флагом `g`, а функция разбора строчной разметки
рекурсивна. У регулярного выражения с `g` есть изменяемое поле `lastIndex`:
вложенный вызов сбрасывал его, внешний цикл начинал разбирать ту же позицию
заново и уходил в бесконечный цикл. Любое сообщение вида `**жирный с `кодом`**`
намертво вешало renderer. Регулярное выражение теперь создаётся на каждый
вызов. Поймано тестом: `executeJavaScript` переставал отвечать.

**Конфликт IPC-каналов.** Новый файловый модуль занял канал `files:list`,
уже зарегистрированный для промптов агентов, — Electron бросает исключение
при повторной регистрации обработчика. Каналы промптов переименованы
в `prompts:*`.

**Осиротевший файл в сборке.** `tsc` не удаляет вывод для исходников,
которые исчезли: после удаления `session-logger.ts` его `.js` оставался
в `dist/` и продолжал подключаться. Добавлена очистка перед сборкой.

**Тесты не были изолированы.** Наборы писали в общий профиль Electron:
состояние копилось между прогонами (поиск находил лишние сообщения),
а тестовый ключ Moonshot попал в общий профиль. Теперь каждый набор
поднимает свой `userData`.

### Перенос данных со старой версии

Проверка на копии реального профиля выявила, что переход ломает историю:
переписка лежала в `sessions.json` (журнал сессий), а новое хранилище чатов
его не читает — 52 КБ диалогов просто перестали бы отображаться.

Добавлен перенос при первом запуске: сессии раскладываются по парам
«первый проект + агент», дубли схлопываются (старый код мог сохранить один
диалог несколько раз), порядок восстанавливается по времени. Исходный
`sessions.json` **не удаляется** и остаётся резервной копией.

Задачи и память переносятся аналогично: плоский массив задач и одиночный
объект памяти уходят в первый проект. Имя-заглушка «Untitled Project»
заменяется на название проекта — иначе она попадала в системный промпт
как название.

Проверено на настоящих данных: 22 сообщения из 6 сессий (21 у Admin, 1 у
Worker1), задача и настройки на месте, файл с ключами не тронут.

## Версия 1.3 — чат как рабочий инструмент

Диалог с агентом до этого был списком сообщений и полем ввода. Всё, что
хотелось сделать с конкретным ответом — скопировать кусок, переспросить
иначе, убрать неудачную попытку, — делалось мимо приложения.

### Панель инструментов и настройки

Над перепиской появилась полоса: счётчик сообщений, кнопка настроек и
очистка диалога с подтверждением (очистка необратима, а промахнуться по
ней легко). Настройки — всплывающая панель: размер текста S/M/L, ширина
колонки, показывать ли время и модель у каждого ответа, звук по окончании
ответа.

Хранятся они в общем `app-settings.json` через `api:getSettings` /

и localStorage там ведёт себя непредсказуемо между запусками.

### Действия над сообщением

По наведению у сообщения появляются «копировать», «изменить», «повторить»
и «удалить». Изменение и повтор перестраивают диалог целиком: renderer
знает, что должно остаться, и отправляет готовый список через `chat:set` —
в хранилище нет отдельных операций «удалить сообщение №N», иначе main и
renderer разошлись бы в понимании того, что такое «повторить ответ».

Добавлена кнопка «к последнему сообщению»: при длинной переписке
прокрутка вручную к концу — лишняя работа.

## Версия 1.5 — конвейер

Главная версия: приложение перестало быть набором чатов. Пользователь
описывает задачу как заказчик, а на выходе получает проект, написанный
воркерами и проверенный тестером. Единственная остановка — утверждение
плана.

### Где он живёт

`src/main/orchestrator.ts`, main-процесс. Не в renderer: тот
перерисовывается, переключает проекты и панели, и конвейер умирал бы
вместе с каждой такой сменой. Автомат состояний: `planning →
awaiting_plan → working → verifying → fixing → done/failed`.

Конвейер пишет в обычные чаты агентов и в дерево задач, поэтому старые
панели показывают тот же прогресс — отдельного «журнала конвейера»,
расходящегося с чатами, не появилось.

### Воркер видит проект

`src/main/code-context.ts` собирает для промпта дерево файлов и содержимое
тех, что вероятнее всего нужны: сначала манифесты (из них виден стек и
скрипты сборки), затем совпавшие с ключевыми словами подзадачи, затем
остальные от корня вглубь. Бюджет — 48 000 символов, на файл — 24 000:
один автогенерённый модуль иначе вытеснит всё остальное.

Без этого агент может только сочинять файлы с нуля — дорабатывать
существующий код физически нечем.

### Проверки настоящие

`src/main/command-runner.ts` запускает то, что действительно есть в
проекте: `npm ci`/`install`, `tsc --noEmit`, `build`, тесты; для Python —
`pip install`, `compileall`, `pytest`. Вывод обрезается с головы и хвоста:
полный лог сборки не влезет в контекст модели, а нужен из него в основном
хвост с ошибками.

Это выполнение произвольного кода — npm-скрипты проекта делают что угодно.
Запускается только перечисленное в `planChecks()` и только в папке проекта.

### Единственная остановка

`PlanApproval.tsx` показывает план до начала работы: порядок подзадач,
исполнителей и формулировки можно править. План дешевле поправить здесь,
чем разбирать десяток файлов, написанных не по тому плану.

### Найденная при проверке ошибка

**Отправка события в закрытое окно роняла конвейер.** Конвейер живёт в
main и переживает закрытие окна, но `webContents.send` в уничтоженный
объект бросает исключение — необработанное отклонение промиса убивало
прогон целиком. Теперь перед отправкой проверяется, жив ли webContents.

### Живой прогон на настоящем ключе

Утилита `slugify` с транслитерацией кириллицы: `done` за 164 секунды,
$0.067. Admin вернул валидный JSON с первой попытки, воркеры соблюдали
`path=` идеально (длина прозы до первого блока — 0 символов во всех
ответах), `npm install` и `npm test` прошли по-настоящему.

Прогон выполнялся на копии профиля (`app.setPath('userData', копия)` до
`whenReady`): реальные проекты, чаты и счётчик расхода не затрагиваются.
Ключ расшифровывается из копии нормально — DPAPI на Windows привязан к
учётной записи, а не к пути. Копия профиля с ключом удаляется после
прогона.

### Что прогон вскрыл

1. Воркеры делают больше, чем просили: подзадача «реализация» создала
   заодно тест, а подзадача «тест» переписала его своей версией.
   Откатиться было некуда.
2. Гейт слабее, чем кажется, на чистом JS: `tsc` и `build` не запускались
   (не было ни `tsconfig.json`, ни скрипта), а статус всё равно стал
   `done`.
3. Frontend-воркер не был задействован — сценарий с двумя исполнителями
   и ошибкой на их стыке живьём не проверялся.

## Версия 1.6 — конвейер, доведённый до автономности

Версия закрывает всё, что вскрыл живой прогон 1.5, плюс два дефекта,
найденных тестами по дороге.

### Воркер может попросить недостающий файл

Контекст ограничен бюджетом, и нужного файла в нём может не оказаться. По
инструкции воркер в таком случае называет файл одной строкой без кода —
а оркестратор такой ответ не обрабатывал: блоков кода нет, значит
подзадача провалена.

Теперь ответ без кода сверяется с деревом проекта. Названные файлы
досылаются принудительно (они идут первыми и включаются даже сверх
бюджета), и задание повторяется один раз. Ответ без кода и без единого
узнаваемого имени файла по-прежнему считается провалом — иначе конвейер
крутил бы пустые раунды.

### Отчёт Тестера влияет на приёмку

Раньше вердикт выносился только по коду возврата сборки, а `[CRITICAL]`
из отчёта писался в чат и игнорировался. Теперь критическое замечание
отправляет код на переделку наравне с падением сборки, а неисправленное
после трёх попыток не даёт принять работу.

Строку-легенду («отчёт в формате [CRITICAL] / [WARNING] / [OK]») модель
повторяет охотно — она отбрасывается, как и метка без текста после неё.
Промпт Тестера переписан: метка `[CRITICAL]` теперь стоит денег и времени,
поэтому в нём прямо сказано, что стиль и отсутствие тестов — это
`[WARNING]`.

### «Проверять было нечем» — отдельный исход

Если в проекте нет ни `package.json`, ни `requirements.txt`, запускать
нечего. Раньше такой прогон становился `done`. Появился статус
`unverified`: код написан, но никто его не запускал. Выдавать это за успех
нельзя — пользователь должен видеть разницу.

### Прогон переживает перезапуск

Состояние лежало переменной в памяти и терялось вместе с приложением.
Теперь прогоны хранятся в `pipeline.json` с ключом по проекту. Прогон,
застигнутый закрытием посреди работы, при старте помечается
`interrupted` — показывать «выполняется» для того, что уже никто не
выполняет, значит врать.

Исключение — прогон, ждущий утверждения плана: план уже оплачен и лежит
целиком, поэтому он восстанавливается живым и гейт можно пройти после
перезапуска.

### Кому чинить

`pickFixer()` брал первое совпадение файла в тексте ошибки, а при неудаче —
первого исполнителя. Теперь побеждает файл, названный в трассе **раньше
всех**: трасса начинается с места падения. Если ни один файл проекта не
назван, а работали оба воркера, исполнителя выбирает Admin одним вопросом
с ответом в одно слово.

### История: снимок после каждого шага

`src/main/git-snapshot.ts`. Папка проекта берётся под git, и после каждой
подзадачи, каждой починки и после проверок создаётся коммит. Это ответ на
пункт 1 из разбора 1.5: перезаписанный чужой файл теперь достаётся из
истории обычным `git show`.

Детали, без которых это не работает: `.gitignore` пишется до первого
коммита (иначе `npm install` притащил бы в историю десятки тысяч файлов);
git запускается **без** `shell: true`, иначе оболочка разберёт сообщение
коммита с пробелами и кавычками на части; пустой коммит не создаётся —
шаг, ничего не изменивший, не должен оставлять след; локальная подпись
проставляется только при отсутствии глобальной и только в своём
репозитории. Если git не установлен, конвейер работает как раньше: снимки
— страховка, а не условие работы.

### Миграция промптов по версии

Посев не перезаписывает существующие файлы, поэтому после обновления
приложения у пользователя оставались бы промпты от старой версии — а
конвейер рассчитывает на новые формулировки. Появились `PROMPTS_VERSION`
и список хэшей всех ранее отгруженных вариантов: файл, чей текст дословно
совпал с одним из них, никто не правил, и его можно молча обновить. Любое
расхождение — работа пользователя, и она остаётся нетронутой.

### Найденные при проверке ошибки

**Имя файла находилось внутри другого имени.** Воркер попросил `spec.md`,
а оркестратор дослал заодно `c.md` — потому что «c.md» лежит внутри
«spe**c.md**». Тот же дефект сидел в выборе чинильщика и мог отправить
починку не тому воркеру. Совпадение теперь засчитывается только на границе
имени.

**Окно плана нельзя было отменить.** Кнопка ставила флаг остановки, но на
гейте цикл не крутится и заметить флаг некому — окно оставалось висеть.

## Версия 1.7 — приёмка работающего приложения

Проверка настоящего заказа, сделанного конвейером, показала границу гейта. Код
собирался, тест проходил, статус был «Готово» — а в приложении нашлось шесть
дефектов, из которых четыре видны за две минуты, если его просто запустить:
нет команды запуска, поле `main` указывает на несуществующий файл, битый JSON в
запросе возвращает HTML со стек-трейсом и путями сервера, а сообщения об
ошибках выдают текст JS-исключения вместо внятного ответа.

### Почему они проходили насквозь

Приёмка умела ровно одну форму проверки: запустить команду, дождаться, пока она
завершится сама, взять код возврата. `npm ci`, `tsc --noEmit`, `build`, тесты —
все они кончаются. Сервер не кончается никогда, и вердикт по коду возврата для
него не существует. Целый класс дефектов оказался за границей измеримого.

### Подними и постучись

`src/main/runtime-check.ts`. После успешной сборки проект запускается тем же
способом, каким его запустит заказчик: `npm start`, иначе поле `main`, иначе
привычная точка входа. Отсутствие штатной команды — уже замечание, потому что
именно об это заказчик спотыкается первым.

Дальше приложение опрашивается: корень, найденные в исходниках маршруты, а для
POST — три заведомо кривых запроса (без тела, битый JSON, пустой объект). Ответ
`5xx`, трасса исключения в теле, текст внутренней ошибки JavaScript, HTML вместо
JSON на `/api/` — всё это замечания с указанием конкретного запроса.

Страница открывается в **скрытом BrowserWindow**: браузер уже лежит в коробке,
Electron — это Chromium, поэтому ни Playwright, ни лишних 300 МБ не понадобилось.
Оттуда берутся ошибки консоли и факт, что в теле документа есть хоть что-то
видимое. Страница написана моделью, поэтому окно создаётся без доступа к Node,
с изоляцией контекста и в песочнице, а попытки открыть новое окно запрещены.

Замечания делятся на блокирующие и справочные. Блокирующие идут в цикл
исправления наравне с падением сборки и не дают принять работу; справочные
попадают в отчёт и Тестеру, но приёмку не останавливают — так относительный путь
в `express.static('public')` виден, но не превращает работающий проект в провал.

Библиотека или утилита из-под проверки выпадает целиком: если в зависимостях нет
веб-фреймворка и нет `public/index.html`, поднимать нечего, и статус от этого не
страдает.

### Найденная при проверке ошибка

**Проверка прятала тот самый дефект, ради которого делалась.** Первая версия
запускала сервер с `NODE_ENV=production` — а Express именно в этом режиме
перестаёт отдавать трассу в своём обработчике по умолчанию. Утечка стек-трейса
переставала воспроизводиться. Переменная больше не выставляется: заказчик
запускает без неё, и проверка тоже.

**Тест умирал молча.** Набор проверок создаёт скрытое окно и уничтожает его, а
Electron по умолчанию выходит из приложения, когда закрылось последнее окно.
Прогон обрывался, не напечатав ни строки, и оставлял за собой живые тестовые
серверы. В наборе теперь стоит пустой обработчик `window-all-closed`.

**Один дефект прятал остальные.** Сломанное поле `main` останавливало проверку
на первом же замечании: запустить по нему нельзя, а до опроса дело не доходило.
Теперь замечание записывается, а поиск точки входа продолжается — на настоящем
заказе это дало четыре находки вместо одной.

## Версия 1.8 — Тестер проходит сценарий пользователя

Запуск и опрос endpoint'ов закрыли класс дефектов «приложение не работает».
Осталось то, что видно только глазами: приложение работает, но делает не то.
В разобранном заказе такой дефект был — флажки «сделано» нарисованы и тут же
отключены. Ни сборка, ни тесты, ни запросы, ни ошибки консоли его не видят:
снаружи всё исправно.

### Кто пишет сценарий

Тестер. Пока приложение поднято и страница открыта, ему отдаётся снимок
страницы — заголовок, список интерактивных элементов с готовыми селекторами
(включая пометку «отключён») и начало разметки — вместе с целью проекта. В
ответ он присылает главный пользовательский путь списком шагов.

**Модель присылает данные, а не код.** Шагов ровно шесть видов: `fill`, `click`,
`waitFor`, `expectText`, `expectChecked`, `expectEnabled`. Каждый превращается в
короткий заранее написанный фрагмент, значения подставляются через
`JSON.stringify`. Никакой текст от модели в браузере не выполняется. Разбор
строгий: неизвестное действие, шаг без селектора и сценарий без единой проверки
отбрасываются целиком — заполнить поле и нажать кнопку можно и в сломанном
приложении.

### Что считать провалом

Разделение оказалось важнее самой механики.

- **Отключённый элемент** (`click` по `disabled`) — блокирует приёмку. Это ровно
  случай мёртвых флажков: пользователь физически не может ими воспользоваться.
- **Обещанного результата не появилось** (`expectText`, `expectChecked`,
  `expectEnabled`) — блокирует. Приложение не делает того, ради чего написано.
- **Элемента для действия нет** — только замечание. Тестер мог выдумать
  селектор, и превращать это в провал нельзя.
- **Не дождались элемента** — замечание, но сценарий **не обрывается**. Это
  и есть развязка: если следующий шаг проверяет обещанный результат и он тоже не
  сходится, дело не в выдуманном классе, а в приложении.

Последнее правило появилось не сразу — его подсказал тест. В первой версии
сценарий обрывался на несостоявшемся ожидании, и приложение, которое молча не
показывало добавленную задачу, проходило приёмку. Ожидание элемента теперь
судится не само по себе, а по тому, что было обещано пользователю.

## Версия 1.9 — оформление: измеритель и дизайнер

Приложение к этому моменту умело отвечать на вопросы «собирается ли», «работает

Проверка живого заказа дала честный ответ — нет: одинаковые отступы везде,
заголовок одного веса с основным текстом, серый текст на белом, синяя кнопка из
первого попавшегося набора. Не уродливо — **никак**.

### Зрения нет, и это выяснилось до начала работы

Первой мыслью было показать модели скриншот. По ключу пользователя доступны
четыре модели Moonshot, ни одна не принимает изображения, ключа Anthropic в
профиле нет — «сфотографировать результат для модели» оказалось некому.

Это к лучшему. Модель, разглядывающая собственный PNG, — плохой арт-директор:
она видит, что «что-то не так», и снова выдаёт медиану. Дело было не в глазах,
а в отсутствии брифа и мерок.

### Мерки вместо зрения

`src/main/layout-audit.ts` снимает со страницы то, что измеримо: контраст текста
к фактическому фону (с подъёмом по родителям до непрозрачной заливки),
отношение крупнейшего заголовка к основному кеглю, число разных значений
отступов, переполнение по горизонтали, длину строки в символах, высоту
кликабельных зон, ограничение ширины содержимого.

Пороги взяты не с потолка: 4.5:1 — норма контраста для основного текста,
полуторный кегль — минимальная различимая ступень иерархии, 60–90 символов —
общепринятая длина строки, 32 пикселя — нижняя граница удобной цели. Всё
остальное вкус, и измеритель туда не лезет.

### Бриф вместо угадывания

Пятый агент — `designer`, со своим промптом в `.claude/agents/designer-agent.md`.
Там лежит дизайн-система по умолчанию: строгая инженерная, с конкретной
палитрой, шкалой кегля 12/14/16/20/28/36 и шкалой отступов 4/8/12/16/24/32/48.
Пользователи таких инструментов живут в таблицах и чертежах, им нужна плотность
и читаемость, а не витрина. Промпт лежит файлом — его правят в панели
«Промпты», а «Память проекта» перебивает систему по умолчанию.

Дизайнеру запрещено трогать логику: обработчики, запросы и имена, по которым
цепляется скрипт, остаются как есть. Меняется оформление, и обычно один файл.

### Цикл замкнут на измерении, а не на обещании

Правка идёт, пока приложение поднято: файлы переписываются на диске, страница
**перечитывается**, мерки снимаются заново. В отчёт попадает «было 6, стало 1»,
а не «дизайнер поработал». Если замечаний стало больше, это отдельная запись в
отчёте — молчать о регрессии нельзя.

Оба замера делаются на одном и том же состоянии страницы, до сценария: иначе
«до» и «после» оказались бы про разные экраны и сравнивать было бы нечего.
Оформление приёмку не блокирует — валить работающий проект из-за отступов
неправильно.

Снимок готовой страницы сохраняется в данные приложения (не в папку проекта,
чтобы не уехал заказчику в архиве) и показывается в панели конвейера. Это и
есть «фотография результата» — но для человека, а не для модели.

### Найденные при проверке ошибки

**Мерки снимались с экрана 800×600.** Скрытое окно создавалось без размеров, и
Electron давал размер по умолчанию. На таком экране длина строки почти всегда в
норме, а проверка «содержимое растянуто на всю ширину» не срабатывала никогда —
она требует ширины от 1100 пикселей. Окно теперь 1280×800: мерки снимаются с
того экрана, на котором приложение реально смотрят.

**Ранний выход пропускал полработы.** Если Тестер не присылал разборчивого

функцию со своими тихими отказами, а шаги проверки идут по порядку без обходных

## Версия 1.10 — что вскрыл настоящий заказ с Excel

Первый заказ, пропущенный через конвейер не из тестового набора, а из работы:
сводник заявок на производство в `.xlsx` и просьба «сделать динамичный график
производства». Результат выглядел солидно — 10 подзадач, React с Vite и
Tailwind, Express с Prisma, docker-compose, 11 коммитов, — и не работал. Разбор
вскрыл две дыры в самом конвейере; обе оказались молчаливыми, что хуже всего.

### Воркер попросил файл заказчика и получил пустоту

В журнале прогона стоит строка «Просит файлы: ПЛАН ПРОИЗВОДСТВА … — досылаю».
Раунд уточнения из версии 1.6 сработал: воркер честно попросил исходные данные,
чтобы посмотреть структуру. Дальше конвейер соврал.

Файл не доехал по двум причинам сразу. Ранжирование включало только знакомые
текстовые расширения, и `.xlsx` отсеивался ещё до чтения; а если бы и дошёл —
`readCapped` отбрасывает всё, где есть NUL-байт. Воркер не получил ни файла, ни
сообщения о том, что файла не будет, и написал разбор вслепую: по типовому
представлению «сводник — это таблица со столбцами заявка, этап, дата начала,
дата окончания».

Настоящий файл устроен иначе: шапка в две строки, этапы — **группы колонок**
(«Подготовительные работы», «Сварные работы», «Передача в покрасочный»,
«Упаковка») по четыре колонки в каждой, план и факт в часах, заказ занимает
несколько строк, номер стоит в одной из них. Запуск сгенерированного парсера на
исходном файле даёт `Could not detect required columns` — приложение не
принимает документ, ради которого написано.

**Что сделано.** `src/main/spreadsheet.ts` читает книгу Excel в текстовое
превью: общие строки, встроенный текст, числа, логические значения и даты,
развёрнутые из серийных номеров по формату ячейки. Без сторонних зависимостей —
`.xlsx` это zip с XML, а распаковка есть во встроенном `zlib`. Нужен не полный
разбор, а точный вид структуры: шапка, порядок колонок, несколько строк данных,
настоящие номера строк. На реальном своднике превью весит 2.5 КБ и совпадает с
эталонным чтением через openpyxl.

Чего прочесть нечем — теперь не исчезает: в контекст уходит честное описание
(«двоичный файл, 14 КБ, содержимое не показано») с прямым указанием не выдумывать
формат, а попросить выгрузку текстом. Журнал перестал врать: рядом с именем файла
пишется, что именно доехало — превью таблицы или только описание.

**Найденная при проверке ошибка.** Первая версия разбора теряла данные:
выражение для строки листа обрывалось на первой самозакрывающейся ячейке
(`<c r="A3" s="5"/>`), а такими записаны пустые ячейки с оформлением — в своднике
их полно. Из 13 строк с данными доезжали 2. Поймал тест на реальном файле,
сверив вывод с openpyxl.

### Гейт пропустил проект целиком

Статус прогона — `unverified`, причина в журнале: «Проверять нечем: не найден
package.json или requirements.txt». Конвейер сам разложил задачу на `backend/` и
`frontend/`, а корневого манифеста не создал — и все проверки, выстроенные в
версиях 1.5–1.9, не выполнились ни одной: ни сборка, ни типы, ни тесты, ни
запуск, ни сценарий, ни вёрстка. Тестер заметил это сам и написал в отчёте
отдельной строкой; конвейер не заметил.

Цена молчания видна на числах: ручная проверка нашла 12 ошибок типов в бэкенде и
одну в фронтенде. Все они лежали ровно на том пути, который не выполнился.

**Что сделано.** `findManifestRoots()` ищет манифесты не только в корне, но и на
два уровня вглубь, пропуская служебные папки. Проверки планируются для каждой
найденной половины, подписи шагов получают имя папки («backend: Сборка»), и у
каждого шага своя рабочая директория.

Запуск приложения устроен тоньше: поднимается та половина, у которой есть
штатная команда запуска, а не первая по алфавиту. Вторая не трогается — у неё
своя сборка, и требовать от бэкенда отдавать страницу фронтенда было бы ложным
замечанием. Поэтому проверка страницы ищет `public/index.html` только внутри
запущенного пакета, а в отчёт добавляется справочная строка о том, что второй
пакет не запускался.

### Проверка версии 1.10

- `npm run typecheck` и `npm run build` — чисто.
- 20 проверок досылки файлов: разбор книги, собранной тем же `archiver`, что уже
  есть в приложении — общие строки, встроенный текст, числа, логические
  значения, даты по формату ячейки, настоящие номера строк, пропуск пустых
  строк; регрессия на самозакрывающуюся ячейку; текст, таблица и двоичный файл
  доезжают с правильной пометкой; запрошенная таблица и описание двоичного файла
  действительно попадают в промпт.
- 17 проверок вложенных манифестов: находятся обе половины, шаги подписаны
  папкой и имеют свою рабочую директорию, проверки реально выполняются и
  проходят, поднимается бэкенд, его маршруты опрашиваются, ложного замечания про
  404 на корне нет, о незапущенном пакете сказано справочно; корневой проект
  по-прежнему один и без префиксов, подпакет внутри проекта отдельным не
  считается, проект без манифестов остаётся «проверять нечем».
- Оба фикса проверены на самом заказе: манифесты находятся оба, план проверок из
  шести шагов, таблица доезжает как превью.

Итого 340 автоматических проверок.

## Версия 1.11 — роль Analyst, живой браузер, параллельные воркеры

Самая большая по объёму сессия с версии 1.6: новая роль в конвейере, вторая
живая проверка помимо Тестера, пять адресных правок по дизайну/скорости и
починка цены самого частого запроса к Claude. Автоматических прогонов на
живом ключе в этот раз не делали — проверка шла через `npm run typecheck`,
`npm test` (vitest, чистые функции разбора) и `npm run build` после каждого
шага, плюс смоук-запуск `npx electron .` без ошибок в выводе. Один живой баг
всё же поймал не тест, а сам пользователь на реальном прогоне — см. ниже.

### Analyst — гейт до Admin, а не только после

Раньше задача сразу уходила Admin. Теперь первым её получает новый агент
`analyst` (`src/main/api-client.ts`, `DEFAULT_AGENTS`) и отвечает JSON'ом:
`feasibility`/`coverage` в процентах и список того, чего не хватает
(`ANALYSIS_INSTRUCTION`, `parseAnalysisOutcome` в `pipeline-parsing.ts`).
Пользователь решает «делать / не делать» в новом гейте `awaiting_analysis` —
первая из теперь уже **трёх** остановок конвейера, а не одной, как было
написано в `HANDOFF.md` до этой правки.

Если задаче не хватает конкретики для честной оценки, Analyst может **один
раз** задать уточняющий вопрос вместо процентов — третий гейт,
`awaiting_clarification`. Ответ пользователя не теряется на границе стадий:
он дописывается в текст задачи, который видит Admin при построении плана
(`approveAnalysis()` в `orchestrator.ts`). Повторно спросить нельзя — сервер
передаёт в `doAnalysis` флаг `allowClarify`, второй раз модель обязана
отвечать числами по тому, что есть.

### Живой браузер — вторая проверка, не только Тестер

Панель «Просмотр» была статичным `<iframe>` на `npm run dev`. Стала
`<webview>` с настоящей консолью (`console-message`), явно ограниченным в
правах так же, как скрытый `BrowserWindow` у Тестера (`contextIsolation`,
без `nodeIntegration`, `sandbox`). Добавлены: кнопка «Прогнать проверки
сейчас» — независимый от конвейера прогон `runtime-check.ts` без сценария и
дизайнера, не тратит бюджет агентов; кнопка «Развернуть» — тот же адрес в
отдельном полноразмерном `BrowserWindow`; автозапуск dev-сервера активного
проекта при старте приложения (тумблер в Настройках, `previewAutoStart`).

**Живой баг, найденный не тестом.** На реальном прогоне пользователь нажал
«Старт» и получил «В package.json нет скрипта dev». Причина — у панели
«Просмотр» и у автопроверки Тестера разная логика поиска команды запуска:
`runtime-check.ts` пробует `start` в первую очередь (и это то, что обычно
кладёт в package.json сам конвейер), а `live-preview.ts` требовал именно
`dev`. Правка: `startPreview()` принимает `dev` **или** `start`, предпочитая
`dev`, если есть оба. Пойман исключительно тем, что человек сам погонял
приложение — ни один из проверочных шагов до этого несовпадение логик не
ловил.

Стадия Тестера («подними и постучись») тоже перестала быть чёрным ящиком:
`runtime-check.ts` получил `onProgress`-колбэк (`RuntimeProgressEvent`),
транслируемый в уже существующий журнал прогона — команда запуска, ответ
сервера, каждый шаг сценария до и после выполнения. Раньше между «Запуск
приложения» и итогом проходило 30–90 секунд тишины.

### Пять адресных правок (дизайн и скорость)

1. Снимок страницы — только после `fill`/`click`, не на чисто проверочных
   шагах (`waitFor`/`expect*`): экран не меняется, кадр не нужен.
2. Дорожка стадий в `PipelinePanel.tsx` (Analyst → Admin → Воркеры → Тестер →
   Готово) поверх статус-строки.
3. Мини-история из 4 последних скриншотов вместо одного перезаписываемого
   файла.
4. Список сообщений в чате рендерится не целиком: кэп 200 + кнопка «показать
   раньше», автоскролл к низу не тронут.
5. Подзадачи Worker1 и Worker2 выполняются параллельно (`runAssigneeQueue` в
   `runRemainder`), а не строго по очереди. Два реальных риска параллелизма
   закрыты явно: `git commit` сериализован общей очередью (`queueSnapshot`),
   а `shouldStop()` проверяет терминальный статус перед логом/`emit()`, чтобы
   остановка, вызванная почти одновременно из двух цепочек, не дублировалась.

### Кэширование системного промпта было включено, но не работало

`system` для Claude собирался одним блоком: промпт агента + контекст
конкретного запроса, склеенные в одну строку. `cache_control` был выставлен,
но раз контекст меняется почти при каждом вызове, кэш промахивался
практически всегда — платили за кэш, не получая от него ничего. Исправлено
разнесением на два блока в `system`: стабильный (`base`, промпт + память
проекта) с `cache_control`, динамический (`extra`, контекст конкретного
запроса) без него.

### Что не вошло

Пробовали добавить воркерам веб-поиск готовых решений (инструмент
`web_search_20250305` из `@anthropic-ai/sdk`, с лимитом запросов и общей
библиотекой находок в `.claude/solutions/`) — реализовали полностью,
прошло `typecheck`/`test`/`build`, но по честной самооценке ценность
оказалась под вопросом (воркеры и так неплохо знают типовые решения по
обучению, воронка до библиотеки узкая — находка сохраняется только если
**весь** прогон дошёл до `done`, а не просто применена), и пользователь
решил откатить до того, как это ушло в git. Код не сохранён нигде, кроме
этого абзаца — если решите делать заново, отправная точка та же: серверный
инструмент Anthropic, а не своя интеграция с поисковиком.
