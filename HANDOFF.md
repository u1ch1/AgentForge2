# Промпт для следующей сессии — AgentForge Studio

Скопируй всё, что ниже, первым сообщением новой сессии.

---

Продолжаю **AgentForge Studio** (`F:\AgenForge\AgentForge2`) — Electron +
React + TypeScript.

## Цель приложения

Это **конвейер для фриланс-заказов по программированию**, а не набор чатов.
Пользователь закидывает задачу как заказчик → на выходе готовый проект,
написанный воркерами и проверенный тестером. Admin координирует.

С версии 1.11 остановок **три**, не одна: сначала Analyst оценивает
выполнимость в процентах (гейт `awaiting_analysis`, при нужде — один
уточняющий вопрос, гейт `awaiting_clarification`), и только если пользователь
согласился делать — Admin строит план (гейт `awaiting_plan`, как раньше).
Дальше всё, как и было, происходит само.

Любое решение по фичам сверяй с этой целью: если оно требует ручного
копирования текста между агентами — оно противоречит цели.

## Архитектура (важное, чтобы не наступить на грабли)

- Строгое разделение main/preload/renderer. Новый IPC — тройное зеркало:
  `src/main/*.ts` (реализация + `ipcMain.handle`) → `src/preload/preload.ts`
  (интерфейс `ElectronAPI` + `ipcRenderer.invoke`) → `src/renderer/types.ts`
  (только типы данных; сам API-surface приходит из preload через `src/types.d.ts`).
- Общий код main+renderer лежит в `src/shared/` (подключён к обоим tsconfig).
  Там `code-blocks.ts` — парсер блоков кода. Не дублируй его.
- **Реальные id агентов**: `analyst`, `admin`, `frontend` (это Worker1),
  `backend` (это Worker2), `tester`, `designer`. «Worker1/Worker2» — только
  `agent.name` для UI. Новую роль достаточно добавить в `DEFAULT_AGENTS`:
  `getAgents()` мержит сохранённый конфиг с дефолтами, так что она появится и
  у старых профилей.
- **Типы конвейера — в `src/shared/pipeline.ts`**, не тройным ручным зеркалом.
  `PipelineRun`/`PipelineSubtask`/`PipelineStatus` и т.п. определены там один
  раз; `orchestrator.ts`, `preload.ts` и `renderer/types.ts` их только
  импортируют и ре-экспортируют. Новое поле добавляй в `shared/pipeline.ts` —
  само появится по цепочке. Остальной новый IPC (не про сам `PipelineRun`)
  по-прежнему тройное зеркало, см. пункт выше.
- Файловые операции строго через `resolveInProject()` (`src/main/projects.ts`).
  У него, у `writeProjectFile()`, `buildProjectContext()` и `listProjectFiles()`
  есть необязательный `projectId` — **конвейер обязан его передавать**:
  пользователь может переключить проект посреди прогона, и без этого файлы
  уедут в чужую папку.
- Настройки — единый `app-settings.json` через `api:getSettings` /
  `api:updateSettings`. Не localStorage (ненадёжно на `file://`).
- Конвейер живёт в **main-процессе** (`src/main/orchestrator.ts`), потому что
  renderer перерисовывается и переключает проекты.
- Состояние конвейера — `pipeline.json`, ключ по проекту. `getRun(projectId?)`
  отдаёт прогон нужного проекта; `emit()` шлёт в окно прогон **открытого**
  проекта, а не работающего.

### Как запускать тесты

Скрипты лежат в скретчпаде сессии, где были написаны:
`C:\Temp\claude\D--AgentForge\79406db7-70b3-42ef-b9c6-e501f2c57759\scratchpad`.
Если их там нет — перепиши по образцу. **Стоит перенести их в репозиторий**
(например, `tests/`), чтобы не зависеть от временных папок.

Ключевое: изолируй профиль (`app.setPath('userData', tmp)`) до `whenReady`,
иначе тест пишет в реальные данные пользователя.

```bash
npm run build && npx electron <путь>/smoke-pipeline2.js
```

### Как делать живой прогон

Только на **копии** профиля: `%APPDATA%/agentforge-studio` → временная папка,
`app.setPath('userData', копия)` до `whenReady`, плюс временная рабочая папка
через `setWorkspaceDir()`. Ключ расшифровывается из копии нормально: DPAPI на
Windows привязан к учётной записи, а не к пути. **Копию профиля после прогона
удаляй** — в ней лежит копия зашифрованного ключа.

Образец: `live-run2.js` в том же скретчпаде. Не пропускай вывод через `head` —
оборванный конвейер вывода убивает процесс до конца отчёта.

## Что осталось

### 1. Живьём не проверены выбор чинильщика и арбитраж Admin
В обоих живых прогонах сборка не падала, поэтому починка не запускалась.
Тестами оба сценария покрыты, но на живых моделях качество ответа Admin
(одно слово «frontend»/«backend») не проверялось. Подстроить падение можно
только искусственно — например, задачей с заведомо несовместимыми версиями
зависимостей.

### 2. Экспорт починен, но раскладка «frontend/backend» ещё жива в других местах
`export.ts` теперь архивирует папку проекта целиком (было: только
`frontend/backend/deploy/.claude` — для проекта из конвейера это давало пустой
архив). Та же устаревшая раскладка осталась в **шаблонах** (`templates.ts`) и в
**генераторе конфигов деплоя** (`deploy.ts`): Dockerfile'ы ссылаются на
`frontend/` и `backend/`, которых у проекта из конвейера нет. Конфиги
подготавливаются, но на настоящем деплое не проверялись — скорее всего,
потребуют правки под фактическую раскладку.

### 3. Откат есть, кнопки нет
Снимки git делаются, история чистая, `git show <коммит>:<файл>` возвращает
любую прежнюю версию. Но из интерфейса откатиться нельзя — нужна панель
истории прогона: список снимков, диффы, кнопка «вернуть файл к этой версии».

### 4. Память проекта берётся от активного проекта, а не от прогона
`getSystemPromptWithMemory()` в `project-memory.ts` читает память через
`getActiveProjectId()`. Тот же класс бага, что был с записью файлов: если
пользователь переключит вкладку проекта посреди прогона, воркеры получат чужую
память. Окно узкое, потерь данных нет — но это прямо подрывает рычаг «стиль
задаётся через память проекта». Лечится прокидыванием `projectId` через
`streamChat` → `getCachedSystemPrompt` → `getSystemPromptWithMemory` (~5 правок).

### 5. У дизайнера нет глаз
Правка идёт по числам и дизайн-системе, а не по картинке: ни одна модель на
ключе пользователя (`kimi-k2.6`, `kimi-k2.7-code`, `kimi-k2.7-code-highspeed`,
`kimi-k3`) не принимает изображения, ключа Anthropic в профиле нет. Снимок
страницы уже делается и лежит в данных приложения — когда появится зрячая
модель, подключить ревью по картинке будет делом одного вызова: у Anthropic это
блок `image` в сообщении.

### 6. Сценарий проходит один главный путь
Тестер описывает главный пользовательский путь, и он проигрывается кликами
(1.8). Но путь ровно один: побочные ветки, вторые экраны и редкие состояния
не проверяются. Расширять стоит осторожно — длинный сценарий чаще ломается сам,
чем ловит дефект, поэтому потолок в 8 шагов стоит не случайно.

### 7. Тестер — самый дорогой агент
В живом прогоне: 6702 выходных токена на отчёт в 15 строк, $0.012 из $0.029
всего прогона (дороже всех воркеров вместе). Стоит посмотреть, не уходит ли
он в длинные рассуждения, и ограничить.

### 8. Прочее
- Автосохранение кода из **ручного** чата (не конвейера) не покрыто сквозным
  тестом — проверялись только части.
- Не проверялось: `npm run dist` (упаковка), сгенерированные конфиги
  Docker/Railway/Vercel на настоящем деплое.
- `MAX_FIX_ATTEMPTS = 3` и бюджет контекста 48 000 символов зашиты в код —
  возможно, им место в настройках.

### 9. Один конвейер на всё приложение, глобально
`if (run && BUSY.includes(run.status)) return run` в `startPipeline()` —
второй проект, пока первый работает, получает отказ, а не встаёт в очередь.
Некритично для одного активного заказа одновременно, но неудобно, если
проектов несколько. Не делали в 1.11 сознательно — пользователь не подтвердил,
что это ему нужно.

### 10. У «Просмотра» нет отдельного смоук-теста на реальном dev-сервере
Баг из 1.11 (`dev` vs `start`) поймал пользователь руками, не тест — потому
что ни один существующий тест не поднимает настоящий `npm start`/`npm run dev`
и не проверяет, что панель реально показывает страницу. Стоило бы завести
тестовый проект-заглушку с обоими вариантами package.json.
